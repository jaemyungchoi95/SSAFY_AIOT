    - 공백문자 인식의 어려움(스페이스, 탭, 줄바꿈)
    - 느린 검색 속도
    - 느린 join 속도
    - 자연키의 높은 수정 가능성 
- 인덱싱
    - DB에서 검색 속도를 빠르게 함 
    - B-Tree 구조: 루트 페이지, 브랜치 페이지, 리프 페이지
    - 각 페이지는 16KB로 크기 고정 
    - 리프 페이지(하단)부터 크기에 맞춰 채워짐
    - 브랜치 페이지에는 어떤 pk 범위 만큼 어떤 리프 페이지에 저장되어 있는지가 저장됨 
    - 루트 페이지에는 어떤 브랜치 페이지에 어떤 pk 범위만큼 저장되어 있는지가 저장됨 
    - 결과적으로 빠른 검색이 가능 
    - 범위 검색의 경우, 최솟값을 찾은 후 자기 옆에 있는 리프 페이지로 이동해 탐색이 가능 -> B+Tree 
    - 만약 검색시 key(정수)가 아닌 값을 이용하는 경우 느림 
- PK를 auto increment로 사용하는 이유 + UUID를 pk로 사용하면 안되는 이유
    - leaf 페이지 순서를 맞추려면(pk 순서) 계속 테이블 위치를 재조정 해야 함 
    - 랜덤 값 또는 순서대로 들어가지 않을 경우 데이터 삽입시 많은 시간이 소요됨 
    - 보안을 위해 UUID를 사용하는 건 성능을 낮춤 
    - 백엔드에서 user id token 권한 확인 후 처리하면 auto increment도 보안 문제 해결 가능 
- varchar vs text
    - varchar는 리프 페이지에 바로 저장됨 -> 탐색 속도 빠름
    - text는 크기 문제로 off-page에 저장되고, 이 off-page의 번호가 리프 페이지에 저장됨 
    - 따라서 text는 속도가 느리고 큰 크기를 가지고 있음

### 2025-08-01
**spot 관련 id 정리**
- Spot ID를 외부(로봇)와 통신하기 위해 UUID를 사용하는 구조 정리
- UUID는 v4 기준 충돌 확률이 사실상 0이므로 전역 유일 ID로 적합
- JSON에서는 항상 문자열 UUID(CHAR(36))로 주고받는 것이 표준
- DB에는 BINARY(16)으로 저장하면 성능과 공간 효율이 훨씬 좋음
- 로봇 → 문자열 UUID 전달 → 자바 서버에서 UUID.fromString() 후 byte[16] 변환 → DB 조회
- Spot 수가 많고 리포트는 적은 구조에서는 UUID 문자열로 받아서 binary 변환 후 조회하는 방식이 가장 실용적
